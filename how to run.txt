Laravel
Framework PHP moderne et élégant pour le développement web. Laravel fournit une architecture MVC (Model-View-Controller) robuste, avec des fonctionnalités intégrées pour le routing, l'authentification, la gestion de base de données (Eloquent ORM), et bien plus.

PHP 8.2+
Langage de programmation côté serveur utilisé pour le backend. La version 8.2+ apporte des améliorations de performance, de nouvelles fonctionnalités comme les enums, readonly properties, et un système de types plus strict.

props:
les props sont des données passées d'un composant parent à un composant enfant, sous forme d'un objet

Objet:
un objet est une structure de données qui stocke des informations sous forme de paires clé-valeur

Composer
Gestionnaire de dépendances pour PHP. Il permet de gérer les packages et bibliothèques nécessaires au projet backend. Le fichier 
composer.json
 définit toutes les dépendances du projet.

PSR-4
Standard de chargement automatique (autoloading) de PHP. Il définit comment les classes doivent être organisées et chargées automatiquement. Dans le projet: "App\\" pointe vers app/, "Database\\Factories\\" vers database/factories/.

Artisan
Interface en ligne de commande (CLI) de Laravel. Fournit des commandes utiles pour créer des migrations, des contrôleurs, des modèles, lancer des tests, et exécuter des tâches personnalisées. Exemple: php artisan migrate, php artisan serve.

Eloquent ORM
Object-Relational Mapping de Laravel. Il permet d'interagir avec la base de données en utilisant des modèles PHP orientés objet plutôt que des requêtes SQL brutes. Chaque table a un modèle correspondant (User, Cryptocurrency, etc.).

Laravel Reverb
Package Laravel pour le WebSocket et la communication temps réel. Utilisé dans ce projet pour diffuser les mises à jour de prix des cryptomonnaies et les événements utilisateur en temps réel.

Migrations
Système de gestion de versions pour les schémas de base de données. Les migrations permettent de créer, modifier ou supprimer des tables et colonnes de manière contrôlée et versionnée.

Seeders
Classes utilisées pour peupler la base de données avec des données de test ou initiales. Utile pour le développement et les tests.

Factories
Générateurs de données factices (fake data) pour les modèles. Utilisées avec Faker pour créer des instances de modèles avec des données aléatoires mais réalistes pour les tests.

Technologies Frontend
React
Bibliothèque JavaScript pour la construction d'interfaces utilisateur. React utilise un DOM virtuel et un système de composants réutilisables. Version utilisée: 18.3.1 avec support des hooks et des fonctionnalités modernes.

TypeScript
Superset de JavaScript qui ajoute un système de types statiques. Permet de détecter les erreurs à la compilation, améliore l'auto-complétion dans les IDE, et rend le code plus maintenable. Version: 5.9.3.

TSX/JSX
Extension de syntaxe pour TypeScript/JavaScript permettant d'écrire du code similaire à HTML directement dans les fichiers TypeScript/JavaScript. 
tsx
 est la version TypeScript de jsx.

React Hooks
Fonctions spéciales de React (useState, useEffect, useContext, etc.) qui permettent d'utiliser l'état et d'autres fonctionnalités React dans les composants fonctionnels.

React Router DOM
Bibliothèque de routing pour les applications React. Permet de créer une navigation côté client (SPA - Single Page Application) avec différentes routes/pages sans rechargement de page. Version: 7.9.5.

Context API
Système de gestion d'état global de React. Utilisé pour partager des données (comme l'état d'authentification, les données utilisateur) entre différents composants sans prop drilling.

Outils de Build & Configuration
Webpack
Module bundler qui compile et empaquète tous les fichiers JavaScript, TypeScript, CSS et autres assets en bundles optimisés pour le navigateur. Version: 5.90.0.

Webpack Dev Server
Serveur de développement pour Webpack qui fournit le rechargement automatique (hot reload) et un serveur HTTP pour tester l'application localement. Port configuré: 3000.

,

) en JavaScript pendant le processus de build.

style-loader

Plugin Webpack qui génère automatiquement un fichier HTML incluant les bundles JavaScript et CSS générés avec leurs hashes de cache.

CopyWebpackPlugin
Plugin Webpack qui copie des fichiers statiques (images, polices, etc.) du dossier public vers le dossier de build dist.

Source Maps
Fichiers qui mappent le code compilé/minifié au code source original. Facilite le débogage en permettant de voir le code TypeScript original dans les outils de développement du navigateur.

Hot Module Replacement (HMR)
Fonctionnalité qui permet de mettre à jour les modules JavaScript en cours d'exécution sans recharger toute la page. Améliore l'expérience de développement.

Base de Données
SQLite
Système de gestion de base de données relationnelle léger, autonome, sans serveur. Utilisé pour ce projet. Les données sont stockées dans un fichier unique (
database.sqlite
).

MySQL/MariaDB
Systèmes de gestion de bases de données relationnelles supportés par Laravel (configurés mais non utilisés dans ce projet). Alternatives à SQLite pour des déploiements en production.

PostgreSQL
Système de gestion de base de données relationnelle objet open-source, également supporté par Laravel (configuré mais non utilisé).

PDO (PHP Data Objects)
Extension PHP pour accéder aux bases de données de manière uniforme et sécurisée. Utilisée par Laravel pour se connecter aux différents types de bases de données.

Foreign Keys
Contraintes de base de données qui assurent l'intégrité référentielle entre les tables. Par exemple, une transaction de portefeuille doit référencer un utilisateur existant.

Communication Temps Réel
WebSocket
Protocole de communication bidirectionnelle full-duplex sur une connexion TCP. Permet une communication en temps réel entre le client et le serveur sans polling.

Pusher
Service et bibliothèque pour implémenter la communication temps réel via WebSockets. Utilisé côté frontend pour se connecter au serveur Laravel Reverb.

Laravel Echo
Bibliothèque JavaScript qui facilite l'abonnement aux canaux et l'écoute des événements diffusés par Laravel. Fournit une API simple pour les WebSockets.

Broadcasting
Système de diffusion d'événements de Laravel. Permet de diffuser des événements côté serveur (comme une mise à jour de prix) à tous les clients connectés en temps réel.

Channels (Canaux)
Espaces de diffusion pour les événements WebSocket. Il existe des canaux publics (crypto-prices) et privés (user.{id}) nécessitant une authentification.

Events (Événements)
Classes PHP qui représentent des événements métier dans l'application (ex: CryptoPriceUpdated, TransactionCompleted, UserBalanceChanged). Peuvent être diffusés via broadcasting.

Architecture & Patterns
MVC (Model-View-Controller)
Pattern architectural utilisé par Laravel. Sépare la logique métier (Model), la présentation (View), et le contrôle de flux (Controller).

RESTful API
Architecture d'API basée sur HTTP utilisant les verbes standard (GET, POST, PUT, DELETE) et les codes de statut HTTP. Le backend expose des endpoints REST pour le frontend.

Middleware
Couches de filtrage HTTP qui s'exécutent avant ou après les requêtes. Utilisés pour l'authentification (auth:web), le throttling (limitation de requêtes), et CORS.

Service Layer
Pattern où la logique métier complexe est encapsulée dans des services dédiés. Exemple: WalletService gère toute la logique d'achat/vente de cryptomonnaies.

Repository Pattern
Pattern (implicite via Eloquent) où l'accès aux données est abstrait derrière une interface. Les modèles Eloquent agissent comme des repositories.

Dependency Injection
Pattern où les dépendances d'une classe sont fournies de l'extérieur plutôt que créées à l'intérieur. Laravel utilise un conteneur IoC (Inversion of Control) pour gérer cela.

SPA (Single Page Application)
Architecture frontend où l'application charge une seule page HTML et met à jour dynamiquement le contenu sans rechargement complet. React Router gère la navigation.

Bibliothèques Frontend
Chart.js
Bibliothèque JavaScript pour créer des graphiques interactifs (lignes, barres, etc.). Utilisée pour afficher l'historique des prix des cryptomonnaies. Version: 4.5.1.

react-chartjs-2
Wrapper React pour Chart.js qui permet d'utiliser Chart.js avec des composants React. Version: 5.3.1.

nanoid
Générateur d'identifiants uniques courts et sécurisés. Alternative à UUID, plus compact. Utilisé pour générer des IDs dans l'application.

Sécurité & Authentification
Session-based Authentication
Méthode d'authentification où l'état de connexion est stocké côté serveur dans une session. Laravel utilise des cookies de session sécurisés.

CSRF (Cross-Site Request Forgery)
Protection contre les attaques où un site malveillant envoie des requêtes au nom d'un utilisateur authentifié. Laravel génère des tokens CSRF pour chaque session.

CORS (Cross-Origin Resource Sharing)
Mécanisme de sécurité du navigateur qui contrôle les requêtes HTTP entre différents domaines. Le backend configure CORS pour autoriser le frontend à faire des requêtes.

Password Hashing
Hashage sécurisé des mots de passe avant stockage en base de données. Laravel utilise bcrypt par défaut via la directive 'password' => 'hashed'.

Throttling
Limitation du nombre de requêtes qu'un utilisateur peut faire dans un intervalle de temps. Protège contre les attaques par force brute et le spam. Configuration: 60 requêtes/minute.

Authentication Guard
Système de Laravel pour définir comment les utilisateurs sont authentifiés. Le projet utilise le guard web qui gère l'authentification par session.

Sanctum/Passport
Packages Laravel pour l'authentification API (non utilisés dans ce projet qui utilise l'authentification par session web).

Concepts Métier

Monnaie numérique utilisant la cryptographie. Dans le projet, modèle représentant une crypto (Bitcoin, Ethereum, etc.) avec son nom, symbole, et description.

Compte virtuel permettant de stocker et gérer des cryptomonnaies. Chaque client possède un portefeuille avec un solde en euros et des holdings en crypto.

Opération d'achat ou de vente de cryptomonnaie. Enregistrée dans WalletTransaction avec le type (buy/sell), le montant, le prix, et la date.

Holdings
Quantité de cryptomonnaie possédée par un utilisateur. Calculée à partir de l'historique des transactions (achats - ventes).

Price History (Historique de Prix)

Client Account
Compte client avec un solde en euros. Lié à un utilisateur de type "client" (par opposition à "admin").

Commission
Frais prélevés sur chaque transaction (non implémentés dans le code visible mais concept métier potentiel).

1. Euros disponibles

Définition : Votre solde de trésorerie disponible.

Calcul : Il s'agit simplement du solde en euros enregistré dans la base de données de votre compte.

Mises à jour :

Diminue lorsque vous achetez des cryptomonnaies (coût d'achat).

Augmente lorsque vous vendez des cryptomonnaies (produit de la vente).

2. Solde total

Définition : La valeur nette totale de votre compte BitChest.

Calcul : Euros disponibles + Valeur marchande des cryptomonnaies

La valeur marchande des cryptomonnaies correspond à la somme de tous vos avoirs en cryptomonnaies multipliée par leur prix actuel en temps réel.

3. Profit/Perte

Définition : Le gain ou la perte latente sur vos avoirs actuels.

Calcul : Valeur marchande actuelle - Coût total d'acquisition

Valeur marchande actuelle : (Quantité × Prix actuel) pour toutes les cryptomonnaies.

Coût total d'acquisition : Le montant total que vous avez dépensé pour acquérir les cryptomonnaies que vous détenez actuellement. Logique :

Achat : Augmente votre prix de revient (par exemple, acheter 100 € de BTC ajoute 100 € à votre prix de revient).

Vente : Réduit votre prix de revient proportionnellement. Le calcul utilise la méthode du coût moyen pondéré.

Exemple : Si vous avez acheté 2 BTC pour 50 000 € (prix moyen : 25 000 €) et que vous vendez 1 BTC, votre prix de revient diminue de moitié (25 000 €), votre prix d’achat moyen restant inchangé.

Formule récapitulative :

Bénéfice/Perte = (Nombre de BTC détenus × Prix actuel) - (Nombre de BTC détenus × Prix d’achat moyen)













1. Algorithme de Génération Aléatoire des Prix (Le "Moteur de Marché")
Le code se trouve dans 
app/Console/Commands/UpdateCryptoPrices.php
. C'est une commande Artisan qui tourne en boucle infinie (while(true)).

La Logique Mathématique : Pour chaque crypto, à chaque cycle (toutes les 5 secondes par défaut), le système calcule un nouveau prix selon cette formule :

php
// 1. Génération d'un facteur de variation aléatoire
// rand(-20, 20) génère un entier entre -20 et +20
// Divisé par 1000, cela donne un flottant entre -0.02 et +0.02
$variation = (rand(-20, 20) / 1000); 

// 2. Application au prix actuel
// Cela signifie que le prix peut varier de -2% à +2% à chaque cycle
$newPrice = $currentPrice * (1 + $variation);

// 3. Sécurité (Floor)
// Pour éviter que le prix ne tombe à 0 ou devienne négatif
if ($newPrice < 5) { $newPrice = 5.00; }
Pourquoi cette approche ?

Volatilité Réaliste : Une variation de +/- 2% crée des graphiques "vivants" sans être trop chaotiques.
Marche Aléatoire (Random Walk) : Le nouveau prix dépend du précédent, créant des tendances naturelles (haussières ou baissières) sur le court terme, simulant un vrai marché boursier.
2. Pourquoi l'Architecture MVC (Modèle-Vue-Contrôleur) ?
Bien que nous utilisions une architecture "Headless" (API Backend + Frontend séparé), le pattern MVC reste le cœur de Laravel.

A. Modèle (Model) - Le "Cerveau" (Données)

Rôle : Représente la structure des données et les règles métier.
Dans Bitchest : 
User
, 
Cryptocurrency
, 
WalletTransaction
.
Pourquoi ? Eloquent ORM nous permet de manipuler la base de données comme des objets PHP ($user->transactions) sans écrire de SQL complexe. Cela garantit l'intégrité des données.
B. Vue (View) - Le "Visage" (Interface)

Rôle : Ce que l'utilisateur voit.
Dans Bitchest : Ici, c'est particulier. Laravel ne renvoie pas de HTML (Blade), mais du JSON. La véritable "Vue" est votre application React.
Pourquoi ? Découplage total. On pourrait changer tout le frontend (passer à Vue.js ou une app mobile) sans toucher une seule ligne du backend.
C. Contrôleur (Controller) - Le "Chef d'Orchestre"

Rôle : Reçoit la requête, demande les données au Modèle, et renvoie la réponse.
Dans Bitchest : 
WalletController
, AuthController.
Pourquoi ? Organisation. Le contrôleur ne contient pas de logique métier complexe (déplacée dans 
WalletService
) ni de code SQL. Il ne fait que coordonner.
Résumé pour le Jury :

"J'ai choisi MVC pour la Séparation des Préoccupations (Separation of Concerns). Cela rend le code :

Maintenable : Si je veux changer le calcul du solde, je vais dans le Service/Modèle, pas dans l'interface.
Testable : Je peux tester mes Modèles indépendamment de l'interface.
Collaboratif : Un développeur peut travailler sur le Frontend (Vue) pendant qu'un autre travaille sur le Backend (API)."


1. Différence de Rôle
Ces deux fichiers gèrent des aspects différents de l'état de votre application : l'Identité vs les Données.

AuthContext.tsx
 (L'Identité / Le Videur)
Rôle principal : Gérer la session de l'utilisateur courant. Il sait qui est connecté.
Ce qu'il contient :
L'objet user actuel (celui qui est connecté).
Le booléen isAuthenticated (est-ce qu'on est connecté ?).
Les fonctions de sécurité : login, logout, changePassword.
Analogie : C'est votre carte d'identité et vos clés de maison. Il permet d'entrer dans l'application.
AppStateProvider.tsx
 (Le Cerveau / La Base de Données)
Rôle principal : Gérer les données métier de l'application. Il contient ce que l'utilisateur voit et manipule.
Ce qu'il contient :
La liste des cryptomonnaies et leurs prix (cryptoAssets).
Les comptes clients, soldes et transactions (clientAccounts).
La liste de tous les utilisateurs (pour l'admin) (users).
Les services métier : createClient, recordTransaction, fetchCryptoAssets.
Analogie : C'est le contenu de la maison (les meubles, l'argent dans le coffre, les dossiers).
2. Comment communiquent-ils ?
Techniquement, ils sont indépendants et ne s'importent pas l'un l'autre directement. Ils communiquent de manière indirecte grâce à l'architecture de votre application (dans 
App.tsx
).

A. La Hiérarchie (Nesting)
Dans 
App.tsx
, ils sont imbriqués comme ceci :

tsx
<AppStateProvider>      {/* Fournit les outils de données (API, Store) */}
  <AuthProvider>        {/* Utilise l'API pour gérer la session */}
    <AppRoutes />       {/* Les pages utilisent les DEUX contextes */}
  </AuthProvider>
</AppStateProvider>
Cela signifie que n'importe quel composant dans 
AppRoutes
 peut accéder aux deux contextes simultanément.

B. Le "Pont" par les Composants
Ce sont vos pages (Composants) qui font le lien entre les deux.

Exemple lors du Login :
L'utilisateur clique sur "Se connecter".
Le composant appelle login() du AuthContext.
Une fois connecté, le composant (ou le Dashboard) appelle fetchClientAccount() du AppStateProvider pour charger le solde de cet utilisateur.
C. Synchronisation des données
Un point de contact important est la mise à jour du profil.

Action : Vous modifiez votre nom dans le profil.
AppStateProvider : Appelle l'API (updateCurrentUserProfile) pour sauvegarder en base de données.
AuthContext : Doit être informé pour mettre à jour l'objet user en mémoire (via sa fonction updateUser), sinon l'affichage du nom en haut à droite ne changera pas, même si la base de données est à jour.
En résumé
Caractéristique	AuthContext.tsx	AppStateProvider.tsx
Sujet	L'Utilisateur (Moi)	L'Application (Le Monde)
Données	Mon ID, mon email, mon rôle.	Prix du Bitcoin, soldes des clients, liste des users.
Actions	Se connecter, Se déconnecter.	Acheter, Vendre, Créer un client.
Persistance	Session (Cookie/Token).	LocalStorage (Cache des données).
Ils travaillent main dans la main : AuthContext ouvre la porte, et AppStateProvider meuble la pièce.






































Authentification et sécurité des mots de passe :

Mécanisme : Utilise l’authentification sécurisée par session de Laravel (auth:web).

Hachage : Les mots de passe ne sont jamais stockés en clair. L’application utilise un hachage robuste (Bcrypt/Argon2) via Hash::make() et Hash::check().

Protection : Le modèle User masque explicitement les champs password et remember_token dans les réponses JSON, empêchant ainsi toute fuite accidentelle.

Validation des entrées :

Règles strictes : Les contrôleurs appliquent des règles de validation strictes. Par exemple, ClientController vérifie la longueur des chaînes de caractères et valide les formats d’adresse e-mail à l’aide d’expressions régulières strictes.

Assainissement : Grâce à l’ORM Eloquent de Laravel, l’application est protégée contre les attaques par injection SQL, car toutes les requêtes utilisent des requêtes préparées.

Contrôle d’accès (autorisation) :

Basé sur les rôles : Des vérifications manuelles sont implémentées dans les contrôleurs (par exemple, if (user->role !== 'admin')) afin de garantir que les clients ne puissent pas accéder aux fonctionnalités d’administration et inversement. Limitation du débit :

Protection de la connexion : La route de connexion est soumise à une limitation de débit stricte (5 requêtes par minute) afin de prévenir les attaques par force brute.

Protection de l’API : Les routes authentifiées sont limitées à 60 requêtes par minute afin de prévenir les abus.

CORS (Partage de ressources entre origines) :

Accès restreint : L’API est configurée pour n’accepter que les requêtes provenant d’origines de confiance spécifiques (par exemple, http://localhost:3000), empêchant ainsi les sites web non autorisés d’accéder à votre API.

1. AuthSession (Le "Passeport" - Backend)
C'est la base de tout. C'est le Cookie HttpOnly sécurisé géré par Laravel.

Rôle : Il prouve au serveur que vous êtes connecté.
Sans lui : Aucune requête API privée ( /api/user, /api/wallet) ne fonctionne. Le serveur répondrait 401 Unauthorized.
2. AuthContext (L' "Identité" - Frontend)
C'est le premier domino à tomber côté React.

Action : Au chargement de la page (
App.tsx
), il appelle /api/auth/me.
Si AuthSession est valide : Le backend répond avec les infos de l'utilisateur.
Résultat : 
AuthContext
 remplit la variable user (id, email, role).
Relation : Il transforme la Session technique (cookie) en Identité utilisable (objet JS).
3. AppState (Le "Coffre-fort" - Frontend)
C'est lui qui stocke vos sous et vos cryptos.

Dépendance : Il attend que 
AuthContext
 ait fini son travail.
Logique :
Tant que AuthContext.user est null -> 
AppState
 ne charge rien (ou juste les prix publics).
Dès que AuthContext.user existe -> 
AppState
 lance fetchClientAccount(user.id).
Relation : Il a besoin de l'Identité pour savoir quel Coffre ouvrir.
4. WebSocket (Le "Téléphone Rouge" - Temps Réel)
C'est le dernier maillon pour la mise à jour instantanée.

Dépendance : Il a besoin de l'ID utilisateur fourni par 
AuthContext
.
Action : Il s'abonne au canal privé private-user.{id}.
Boucle de retour :
Le Backend envoie un événement "Solde mis à jour".
Le WebSocket le reçoit.
Il envoie un signal à 
AppState
 (dispatch).
AppState
 met à jour le solde à l'écran sans recharger la page.
Résumé Visuel pour le Jury
Imaginez une Maison Sécurisée :

AuthSession : C'est la Clé physique dans votre poche.
AuthContext : C'est le Portier qui vérifie la clé et vous laisse entrer dans le hall.
AppState : C'est votre Chambre. Vous ne pouvez pas y aller tant que le portier ne vous a pas laissé entrer.
WebSocket : C'est l'Interphone dans votre chambre. Il ne sonne que si vous êtes dans la chambre pour l'entendre.
Flux Technique : Cookie (Session) ➡️ API /me ➡️ AuthContext (User) ➡️ AppState (Fetch Data) ➕ WebSocket (Subscribe)


Cette architecture en couches (middleware → authentification → autorisation → validation métier) suit le principe de défense en profondeur, où chaque couche ajoute une protection supplémentaire contre les accès non autorisés.

Analyse Détaillée des Mesures de Sécurité - BitChest
Ce document explique les 7 piliers de sécurité implémentés dans le projet, en détaillant pour chacun le mécanisme, le code concerné et la menace qu'il neutralise.

1. 🔐 Hachage de mots de passe (Data Integrity)
Fichier concerné : 
backend/app/Http/Controllers/AuthController.php
Menace prévenue : Vol de données (Data Theft / Leaks)
📘 Explication
Stocker des mots de passe en clair dans une base de données est une faille critique. Si la base est piratée, tous les comptes sont compromis. Nous utilisons Bcrypt, un algorithme de hachage lent et robuste.

💻 Code Snippet
Dans 
AuthController.php
, lors du changement de mot de passe ou de la création de compte :

use Illuminate\Support\Facades\Hash;
// Création du hash avant le stockage
$user->password = Hash::make($request->newPassword);
// Vérification lors du login (Comparaison Hash vs Texte clair)
if (!Hash::check($request->password, $user->password)) {
    return response()->json(['message' => 'Invalid credentials'], 401);
}
2. ⏱️ Rate Limiting (Throttle)
Fichier concerné : 
backend/routes/web.php
Menace prévenue : Attaques Brute-force
📘 Explication
Une attaque brute-force consiste à essayer des milliers de combinaisons email/mot de passe par seconde. Le "Throttling" limite le nombre de requêtes autorisées par IP dans un laps de temps donné.

💻 Code Snippet
Dans 
web.php
 :

// Limite à 5 tentatives par minute pour le login
Route::post('/auth/login', [AuthController::class, 'login'])
    ->middleware('throttle:5,1');
// Limite à 60 requêtes par minute pour les routes API authentifiées
Route::middleware(['auth:web', 'throttle:60,1'])->group(function () {
    // ...
});
3. ✅ Validation des entrées
Fichier concerné : 
backend/app/Http/Controllers/AuthController.php
Menace prévenue : Injection SQL, XSS, Données corrompues
📘 Explication
Ne jamais faire confiance aux données envoyées par l'utilisateur. La validation filtre les données avant qu'elles n'atteignent le code métier ou la base de données. Bien que Eloquent protège contre les Injections SQL, la validation est la première ligne de défense stricte.

💻 Code Snippet
Dans 
AuthController.php
 :

$request->validate([
    'email' => 'required|email', // Doit être un format email valide
    'password' => 'required|string', // Doit être une chaîne
    // Validation complexe avec Regex pour la sécurité du mot de passe
    'newPassword' => 'required|string|min:8|regex:/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[@$!%*?&])[a-zA-Z\d@$!%*?&]{8,}$/',
]);
4. 🛡️ CSRF Protection (Cross-Site Request Forgery)
Fichier concerné : 
backend/bootstrap/app.php
 et 
backend/app/Http/Controllers/AuthController.php
Menace prévenue : Attaques CSRF
📘 Explication
Une attaque CSRF force un utilisateur authentifié à exécuter des actions à son insu (ex: changer son mot de passe en cliquant sur un lien piégé). Laravel utilise des tokens CSRF pour vérifier que la requête vient bien de l'application légitime.

💻 Code Snippet
Dans 
AuthController.php
 (Régénération après actions critiques) :

// Régénère le token de session pour empêcher les attaques de fixation
$request->session()->regenerateToken();
Dans 
bootstrap/app.php
 (Configuration) :

// Laravel active la protection CSRF par défaut pour toutes les routes "web"
$middleware->validateCsrfTokens(except: [
    // Exceptions spécifiques si nécessaire pour certaines routes API publiques
]);
5. 🌐 CORS Configuration (Cross-Origin Resource Sharing)
Fichier concerné : 
backend/app/Http/Middleware/CorsMiddleware.php
Menace prévenue : Requêtes cross-origin malveillantes
📘 Explication
Par défaut, les navigateurs bloquent les requêtes AJAX vers un autre domaine. CORS permet de définir strictement QUI a le droit d'interroger notre API (uniquement notre Frontend).

💻 Code Snippet
Dans 
CorsMiddleware.php
 :

$allowed_origins = [
    'http://localhost:3000', // Frontend React local
    'http://127.0.0.1:3000',
];
// Si l'origine n'est pas dans la liste, la requête est rejetée par le navigateur
if (in_array($origin, $allowed_origins)) {
    $response->header('Access-Control-Allow-Origin', $origin);
    $response->header('Access-Control-Allow-Credentials', 'true');
}
6. 🔑 Authentification par session
Fichier concerné : 
backend/app/Http/Controllers/AuthController.php
Menace prévenue : Accès non autorisé
📘 Explication
Garantit que seules les personnes ayant fourni des identifiants valides peuvent accéder aux ressources protégées. Nous utilisons le système de session de Laravel (Stateful) couplé à Sanctum.

💻 Code Snippet
Dans 
AuthController.php
 :

// Vérifie si les identifiants correspondent
if (!$user || !Hash::check($request->password, $user->password)) {
    return response()->json(['message' => 'Invalid credentials'], 401);
}
// Crée une session sécurisée côté serveur pour cet utilisateur
auth()->login($user);
7. 🚪 Invalidation de session
Fichier concerné : 
backend/app/Http/Controllers/AuthController.php
Menace prévenue : Session Hijacking (Vol de session)
📘 Explication
Lorsqu'un utilisateur se déconnecte, il est crucial de détruire complètement la session côté serveur pour qu'un attaquant qui aurait volé l'identifiant de session (cookie) ne puisse plus l'utiliser.

💻 Code Snippet
Dans 
AuthController.php
 (Méthode logout) :

public function logout(Request $request)
{
    auth()->logout(); // Déconnecte l'utilisateur
    // Détruit toutes les données de la session actuelle
    $request->session()->invalidate();
    // Génère un nouveau token CSRF pour la prochaine session
    $request->session()->regenerateToken();
    return response()->json(['message' => 'Logged out successfully']);
}























Tests Automatisés (PHPUnit)
⚙️ Comment ça marche ?
Contrairement à Postman où l'humain clique sur "Envoyer", ici c'est un script PHP qui exécute les tests.

Fiabilité : Élimine l'erreur humaine lors des tests manuels.

 La Sécurité (Laravel Sanctum)
⚙️ Comment ça marche ?
La sécurité repose sur l'authentification par Tokens (Jetons) via Laravel Sanctum.

Login : L'utilisateur envoie email/password. Si valide, le serveur génère un token crypté (chaîne de caractères unique).
Stockage : Le Frontend stocke ce token (généralement dans le LocalStorage ou en mémoire).
Requêtes : Pour chaque action (ex: acheter crypto), le Frontend envoie ce token dans l'en-tête HTTP (Authorization: Bearer <token>).
Validation : Le Backend vérifie la validité du token à chaque requête.
Nous utilisons aussi des Policies (Politiques) pour l'autorisation : un client ne peut voir que son portefeuille, pas celui des autres.

🎯 Le But
Protéger les données et les fonds des utilisateurs. Assurer que "Qui je suis" (Authentification) et "Ce que j'ai le droit de faire" (Autorisation) sont strictement contrôlés.

💡 Pourquoi l'avoir utilisé ?
Stateless : Idéal pour les APIs et les applications mobiles/SPA (Single Page Applications) comme React.
Standard : Sanctum est la solution officielle légère de Laravel, parfaite pour ce type de projet.
Protection CSRF/XSS : Combiné aux bonnes pratiques React, cela limite les failles web courantes.

Le socle de sécurité.

C'est quoi ? : Un framework PHP moderne et structuré.

L'expérience utilisateur fluide.

C'est quoi ? : Une librairie JavaScript pour créer des interfaces utilisateur.
Pourquoi ce choix ?
Virtual DOM : Indispensable pour le trading. Quand un prix change, React ne met à jour QUE ce chiffre, pas toute la page. C'est ultra-rapide.

La rigueur financière.

SPA Ready : Conçu spécifiquement pour le couple Laravel + React.

L'Eager Loading (ou "Chargement Anticipé") est une technique d'optimisation de base de données utilisée par l'ORM Eloquent de Laravel.

📖 Définition Simple
C'est le fait de demander à Laravel de charger les données liées (relations) en même temps que l'objet principal, en une seule fois (ou très peu de requêtes), au lieu de les charger une par une plus tard.

🔴 Le problème sans Eager Loading : Le "N+1"
Imagine que tu as 10 cryptomonnaies et que tu veux afficher leurs prix historiques. Si tu ne fais pas d'Eager Loading :

Laravel fait 1 requête pour récupérer les 10 cryptos.
PUIS, pour chaque crypto, il fait 1 requête pour chercher ses prix.
Total : 1 + 10 = 11 requêtes. Si tu as 1000 cryptos, tu fais 1001 requêtes, ce qui tue les performances de ton serveur.
🟢 La solution avec Eager Loading
Dans ton fichier 
CryptocurrencyController.php
, tu as ce code :

php
$cryptos = Cryptocurrency::with('prices')->get();
Le mot-clé 
with('prices')
 dit à Laravel : "Prends toutes les cryptos, et AVANT de me les donner, va chercher tous les prix correspondants en une seule grosse requête".

Total : Seulement 2 requêtes, peu importe si tu as 10 ou 1000 cryptos.
